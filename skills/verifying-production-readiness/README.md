# verifying-production-readiness

출하 판정(go/no-go)을 **감사 가능한 기록**으로 만드는 Claude Code 스킬.
초록색 테스트는 출하 근거가 아니다 — 이 스킬은 판정을 **관측**으로만 세우게 하고,
그 판정이 거짓말을 못 하도록 대장을 기계로 검사한다.

- 버전: **0.9.0** (2026-08-24)
- 라이선스/작성: 장욱 (Wook Jang)

```bash

claude plugin marketplace add /경로/vpr-plugin
claude plugin install verifying-production-readiness@verifying-production-readiness
```

**스킬 디렉터리로**: 이 디렉터리를 `~/.claude/skills/verifying-production-readiness/` 에 두면 된다.
Claude Code 가 스킬 목록에서 자동으로 잡는다. 의존성은 `bash` · `python3`(표준 라이브러리만) ·
선택적으로 `git`(저장소 루트 기준 인용 해석에 쓴다. 없어도 동작한다).

```bash
bin/vpr test                  # 설치 확인 — 156 passed, 0 failed 가 나와야 한다
```

## 5분 퀵스타트

처음이면 이 순서만 따라가면 된다. 형식은 기계가 만들고, 규칙은 기계가 검사한다.

```bash
bin/vpr new ~/myproject                  # ① 뼈대 생성 (readiness.md + evidence/)
bin/vpr new ~/myproject --axes 3,5,7     #    볼 축을 착수 시점에 고를 수도 있다
```
축을 고르면 코어 ④사용성·E2E ⑥보안 ⑧논리 ⑨결정성 은 자동으로 들어가고(못 뺀다), 나머지는
뺀 축으로 선언에 남는다. 정식 모드(`--full`)는 고른 축의 파일만 만든다.
② `readiness.md` 의 게이트 표에 **목표를 수치로** 채운다 — 재기 전에. (「테스트 통과」가 아니라
「<스위트> fail 0」처럼 세는 방법까지. 결과를 보고 고치면 판정이 아니라 사후 승인이다.)

③ 감사한다. 명령 출력은 `evidence/` 에 남기고, 발견은 **즉시** 대장 한 줄로 적는다:

```markdown
| SUP-01 | BLOCKER | ⑦ | 프로덕션 도달 high 3건 | open | measured | `evidence/audit.log:3` | — |
```

```bash
bin/vpr lint ~/myproject         # ④ 통과해야 판정이 유효하다
bin/vpr render ~/myproject       # ⑤ 게시용 HTML
```

⑤ 판정은 네 어휘뿐이다: **출하 가능 · 조건부 출하 가능 · 출하 불가 · 판정 불가**.
실측이 하나도 없으면 lint 가 「출하 가능」을 거부한다(R8) — 그때는 조건부(조건 명시) 또는
판정 불가로 내라. 그게 이 스킬의 전부다.

## 쓰는 법

판정을 내려야 할 때 스킬을 부르면 된다("출하해도 되나?", "release readiness 감사").
사람이 직접 돌릴 명령은 셋뿐이다:

```bash
bin/vpr new <프로젝트 경로> [--full] [--axes 3,5,7]   # 뼈대 생성 · 볼 축 선택
bin/vpr lint <리포트|디렉터리>         # 판정 전·재진입 직후 필수 (--strict 로 증거 범위 제한)
bin/vpr render <같은 대상>             # 게시용 HTML (lint 통과 시에만)
bin/vpr rules                          # 규칙 요약 · bin/vpr test 자체 테스트
```

`vpr` 와 각 스크립트는 `--help` 를 받는다. `ledger-lint.sh --strict` 는 증거 인용을 리포트·저장소
안으로 제한한다(기본은 허용 — 시스템 로그를 인용하는 정당한 감사가 있다).

`ledger-lint.sh` 는 **어디서 실행하든 같은 판정을 낸다** — 인용 경로는 리포트 디렉터리 →
저장소 루트(git) → 절대경로 순으로만 찾고, 현재 작업 디렉터리는 기준으로 쓰지 않는다.

## 규칙 요약 (R1–R13)

| | 검사 |
|---|---|
| R1 | `measured` 행은 실존 파일 인용 필수(`파일:줄`이면 줄 번호가 파일 길이 안) |
| R2 | `verified` 행은 「닫은 증거」 필수 |
| R3 | ID 중복 금지 |
| R4 | 심각도·상태·근거등급 어휘 고정 |
| R5 | `rejected`/`deferred` 는 사유 필수 |
| R6 | 헤더 open BLOCKER 정합 · 판정 4어휘 고정 · GO 인데 open BLOCKER 면 위반 |
| R7 | 인용 증거가 0바이트·공백뿐이거나 공백 줄을 가리키면 위반 |
| **R8** | **판정 「출하 가능(GO)」은 실측 근거 없이 낼 수 없다** — measured 대장 행(외부 인용) 또는 게이트 표 실측 칸의 인용이 최소 1건 |
| **R9** | 게이트 표 「실측」칸은 수치 또는 유효 인용이어야 한다. 안 쟀으면 `미실시` 라고 적어라 |
| **R10** | 통과 계열 판정(출하 가능·조건부)은 **게이트 표 없이** 낼 수 없다 — 착수 전 확정한 기준이 문서 어디에도 없으면 그 통과는 기준 없이 난 것이다(Iron Rule 1). 대장 안이든 형제 파일이든 무방 |
| **R11** | 「조건부 출하 가능」은 **조건이 명시**돼야 한다 — 조건부는 R8 의 탈출구라, 조건을 안 적으면 무근거 통과의 우회로가 된다 |
| **R12** | **형제 리포트 파일의 판정이 대장과 갈리면 위반** — 정식 모드는 사람이 읽는 판정이 `00-summary.md` 에 살아서, 요약만 통과로 바꾸면 R6·R8·R10·R11 을 통째로 비켜 갈 수 있었다. 판정을 주장하는 파일은 `open BLOCKER` 헤더 수치도 대장과 맞아야 한다. `**판정**` 마커가 없는 형태(`# 판정` 절 아래 `> ## 출하 가능`·표 행)도 본다 — 그게 `report-template.md` 가 권하는 요약 골격이다. 비교는 **부류**로 한다(「GO」와 「출하 가능」은 같은 판정) |
| **R13** | **축 선택 선언의 정합성** — 코어 축 ④⑥⑧⑨ 는 「뺀 축」에 넣을 수 없다(볼 수 없었던 것은 「나. 확인 불가」다). 통과 계열 판정에서 뺀 축이 있으면 **사유**가 있어야 한다. 선언이 없는 리포트는 검사하지 않는다 |

## 알려진 한계 (의도적)

- **인용의 내용까지는 검사하지 않는다.** 실존하고 비어 있지 않은 파일이면 유효 인용으로 친다 —
  무관한 파일을 가리켜도 기계는 모른다. 그 판단은 재진입 세션이 의심하는 몫이다.
  (절대경로 시스템 로그를 증거로 쓰는 정당한 감사가 있어 경로 범위를 좁히지 않았다.)
- **R12 가 보는 형제 파일은 리포트 가족뿐이다** — `NN-*.md`·`ledger.md`·`readiness.md`·`gates.md`·`fixes-round*.md`. 같은 디렉터리의 `README.md`·`progress.md` 처럼 남의 문서에서 판정 줄을 주우면 거짓 위반이 되므로 일부러 좁혔다. 리포트 가족 밖 파일에 판정을 적으면 검사되지 않는다.
- **셀 안의 날 `|`** 는 구분자로 읽힌다. 마크다운 이스케이프 `\|` 는 지원한다.
- **경로에 공백이 있는 파일**은 인용으로 인식하지 못한다(리포트 경로 자체에 공백은 괜찮다).
- **규모**: 200행대 대장이 약 3초, 2만행은 약 90초다. 실무 대장(수백 행)에는 충분하지만
  기계 생성 대장을 통째로 넣는 용도는 아니다.
- **컨텍스트 비용**: `SKILL.md` 약 8.8k자(대략 7k–12k 토큰) — 0.2.0(10.4k자) 대비 15% 적다.
  참조까지 전량 읽으면 25k자대이므로 **경량 모드가 기본**이고 `axes.md` 는 보는 축의 절만 읽는다.

## 이력

- **0.9.0** (2026-08-24) — **축별 모델 등급 라우팅.** lint 는 형식만 보므로 **하방(거짓 통과)은
  도구가 막고 상방(무엇을 발견하는가)은 모델이 정한다** — 약한 모델은 틀린 판정이 아니라
  **얕은 감사**를 내고 그건 리포트에 「봤는데 괜찮았다」로 적힌다. 그래서 축을 세 등급으로
  나눴다: **설계·판단**(오케스트레이터 · ④ E2E · ⑥ 보안 · ⑧ 논리) · **실행·회수**(도구 결과를
  규격대로 회수하는 축 · 수정 라운드) · **기계적**(evidence 정리 · 형식 수리). 비용을 줄일 땐
  ④⑧ 말고 실행·회수부터 내린다. 축 파일 뼈대가 **감사 모델·위임 도구**를 적도록 바뀌었다 —
  Sonnet 이 본 축과 Fable 이 본 축은 같은 등급의 증거가 아니고, 다음 세션이 재감사 우선순위를
  정하려면 그걸 알아야 한다. 모델 이름은 환경 예시이고 **규약은 등급**이다. 테스트 155 → **156**.
- **0.8.0** (2026-08-24) — **축별 위임 도구를 「다른 렌즈」 기준으로 보강.** ③ 은 시각 품질
  (`/design-review`)과 접근성 규격(`accessibility-review`)으로 갈랐고, 위임 도구가 하나도 없던
  **⑧ 논리에 `/codex`(적대적 반박), ⑪ 관측성에 `/canary`** 를 붙였다. 같은 모달리티를 쌓지 않는
  이유를 `axes.md` 에 명시 — 정적 스캐너를 겹치면 사각이 함께 움직이고 같은 결함이 대장에 두
  줄로 들어온다. `ensure-tools.sh` 에 **스킬 자동 설치**를 넣되 안전 경계를 뒀다:
  **새 마켓플레이스를 스크립트가 추가하지 않는다**(사용자가 이미 신뢰해 등록한 출처에서만 받는다).

  「세션 제공」으로 분리 — 예전에는 이것들을 「없음」으로 세어 멀쩡히 쓸 수 있는 스킬을

- **0.7.0** (2026-08-23) — **축 선택을 산문 규약에서 구조로.** `new-report.sh --axes 3,5,7` 로
