# 리포트 구조 — 다음 세션이 이어받는 근거

**요약 문장이 아니라 결함 대장이 정본이다.** 사람이 쓴 판정문은 낡지만, ID·상태·근거가 붙은 대장은 이어받을 수 있다.

## 디렉터리

```
docs/release-readiness/<YYYY-MM-DD>/
  00-summary.md          판정 · 게이트 실측표 · 축별 한 줄 · 잔여
  ledger.md              🔑 결함 대장 (정본)
  01-features.md  02-backend.md  03-ui.md  04-usability.md  05-perf.md
  06-security.md  07-supply-chain.md  08-logic.md  09-determinism.md
  10-deploy.md    11-ops.md
  fixes-round1.md … fixes-roundN.md
  99-final-verification.md
  evidence/            스크린샷 · 로그 · 명령 출력 (근거 원본)
  report.html          bin/report-html.py 생성물 — Artifact 게시용(같은 경로 재게시로 URL 유지)
```

축 파일 번호는 고정한다. **번호가 고정돼야 다음 세션이 「06 은 보안」임을 안다.**

## 경량 모드 — `readiness.md` 단일 파일 골격

소규모·1세션 검토(SKILL.md 「경량 모드」)는 위 디렉터리 대신 아래 한 파일이 전부다.
대장 표 형식이 `ledger.md` 와 동일해서 `ledger-lint.sh readiness.md` 로 그대로 검사된다.

```markdown
# <대상> 출하 검증 — 경량 모드
**갱신** <날짜> · **판정** <출하 가능|조건부 출하 가능|출하 불가|판정 불가> · **open BLOCKER** 0 · **open 전체** N
대상 `<커밋>` · 축: ④⑧⑨ + <변경이 닿는 축> · 뺀 축: <목록 — 사유>

## 게이트 (착수 전 확정 — Iron Rule 1)
| 게이트 | 목표 | 실측 |

## 결함 대장
| ID | 심각도 | 축 | 한 줄 | 상태 | 근거등급 | 근거 | 닫은 증거 |
|---|---|---|---|---|---|---|---|

## 보지 않은 것
가. 의도적 제외: <사유> · 나. 확인 불가: <누가 무엇을 주면 볼 수 있는지>
```

정식 감사로 승격하면 재진입 절차의 분리 규칙대로 대장을 `ledger.md` 로 떼어낸다.

## `ledger.md` — 결함 대장 (이 스킬의 핵심)

```markdown
# 결함 대장 — <대상> <버전/커밋>

**갱신** 2026-08-16 · **판정** 조건부 출하 가능 · **open BLOCKER** 0 · **open 전체** 12

| ID | 심각도 | 축 | 한 줄 | 상태 | 근거등급 | 근거 | 닫은 증거 |
|---|---|---|---|---|---|---|---|
| SEC-01 | BLOCKER | 06 | 업로더 지정 Content-Type 을 그대로 inline 서빙 (저장형 XSS) | verified | measured | `src/routes/files.ts:412` | `fixes-round1.md` + 회귀 테스트 `files.serve.test.ts:44` |
| PERF-03 | BLOCKER | 05 | 대용량 내보내기가 API 전체를 수 분간 정지 | verified | measured | `04-usability.md` S4 | `fixes-round6.md` · 재측정 p95 1.2s |
| OPS-02 | HIGH | 11 | 배경 작업 실패가 계측되지 않음(예외를 삼킨다) | open | code | `src/jobs/summary.ts:64` | — |
| DEP-04 | HIGH | 07 | critical 1건이 프로덕션 번들에 도달 | open | claimed | 팀 진술만 있음 — **실측 전까지 통과 불가** | — |
| API-17 | MED | 02 | (감사 오류) 이미 수정돼 있었음 | rejected | code | 이전 릴리즈에 반영됨 | 반박 근거 `fixes-round3.md` |
| UX-09 | LOW | 03 | 빈 상태 카피 없음 | deferred | measured | `03-ui.md` §4 | 출하 후 백로그 |
```

### ID 규약
`<축약어>-<번호>` — 축마다 접두사 고정(`FEAT`·`API`·`UX`·`USE`·`PERF`·`SEC`·`DEP`·`LOGIC`·`DET`·`SHIP`·`OPS`).
**한 번 부여한 ID 는 재사용하지 않는다.** 기각된 ID 도 비워 두지 마라 — 다음 세션이 「없어졌네?」 하고 다시 찾는다.

### 상태 수명주기
```
open → fixing → fixed → verified
  ↘ rejected (근거 든 반박 — 사유 필수)
  ↘ deferred (출하 후 백로그 — 언제·왜 미루는지 필수)
```
**`fixed` 와 `verified` 를 구분하는 것이 이 대장의 존재 이유다.** 「고쳤다」는 주장이고 「재측정했다」가 관측이다(Iron Rule 4).

### 「문제 없음」도 행으로 남긴다
확인해서 **괜찮았던 것**도 대장에 넣는다 — 심각도 `—` · 상태 `verified` · 근거등급 `measured`.
남기지 않으면 **다음 세션이 같은 것을 또 확인한다.** 대장은 결함 목록이 아니라 **확인 대장**이다.

### 근거 등급 열
`claimed`(진술만) · `code`(코드로 확인) · `measured`(실제로 돌려 관측). **`measured` 아닌 근거만으로 「출하 가능」을 낼 수 없다.**
자기보고로 올린 차단 후보는 `claimed` 로 열어 두고, 실측 후 등급을 올린다 — **심각도를 낮추지 말고 등급을 올려라.**

## `00-summary.md` 골격

```markdown
# <대상> 출하 검증 — 종합 리포트
**작성 <날짜>** · 대상 `<커밋>` · 방식 <N>축 병렬 감사 + <N> 수정 라운드

# 판정
> ## <출하 가능 | 조건부 출하 가능 | 출하 불가>
> 착수 시점 판정: <…> → 무엇을 고쳐서 어떻게 바뀌었는지 한 문단

**남은 조건**(조건부일 때만): ① … ② …   ← 누가·무엇을·어떻게 확인하면 닫히는지

# 게이트 실측
| 게이트 | 착수 전 | 최종 | 목표 | 비고 |
← 목표 열은 **착수 전에 채운다**(Iron Rule 1)

# 축별 결과
## ① 기능 완성도 — <점수/판정> → `01-features.md`
… 각 축 3~5줄 + 파일 링크

# 이번에 보지 않은 축 — **두 종류를 갈라 적는다**
## 가. 의도적 제외
← 범위 밖이라 안 봤다. 사유 필수
## 나. 확인 불가 — 볼 수단이 없었다
← 접근 권한 없음 · 환경 없음 · **조직도 아직 모름**. 「누가 무엇을 주면 볼 수 있는지」를 함께 적는다

두 칸을 합치면 다음 사람이 「검토했는데 괜찮았다」로 읽는다. **가**는 결정이고 **나**는 미결이다

# 사용자·제품 결정 사항
← 기술 판정이 아니라 사람이 정해야 하는 것

# 출하 후 백로그
← deferred 항목 전부, 근거 파일:줄과 함께

# 이 감사에서 배운 것
← 다음 감사가 그대로 쓸 교훈. **방법론 개선은 여기에 쌓인다**
```

## `fixes-roundN.md` 골격

```markdown
# 수정 라운드 N — <확정 결함 M건> (<날짜>)
- 대상: `06-security.md` [SEC-01] · [SEC-04] · `02-backend.md` [API-02]
- 원칙: 근본 원인 수정 · 외과적 변경 · 건별 회귀 테스트 · 실측 검증

## [SEC-01] BLOCKER — <제목>
**근본 원인** ← 증상이 아니라 원인. 왜 이 코드가 이렇게 됐는지까지
**무엇을 어떻게 고쳤나** ← `파일:줄` 단위
**회귀 테스트** ← 이 결함을 재현하는 테스트. 없으면 사유
**재측정** ← 수정 후 실측값 (Iron Rule 4)
**드러난 다음 결함** ← 있으면 새 ID 로 대장에 추가
```

## 후속 세션 재진입 절차

새 세션은 **이 순서로만** 읽으면 된다. 전체를 다시 읽지 마라.

**재진입 첫 명령은 lint 다** — 대장 무결부터 확인하고 시작한다:
```bash
bash <스킬 디렉터리>/bin/ledger-lint.sh docs/release-readiness/<날짜>/
```
위반이 나오면 **그 정리가 첫 작업이다**(measured 지어내기·근거 없는 verified 가 섞인
대장 위에서 한 작업은 전부 다시 하게 된다).

**앞 세션 산출물이 아직 파일 하나면**(계획 단계에서 시작한 경우가 흔하다), **재진입 첫 작업이 분리다** — 그 파일에서 대장을 `ledger.md` 로 떼어내고 축별 파일 골격을 만든 뒤 아래 절차를 탄다. 분리하지 않고 계속 한 파일에 쌓으면 3회차쯤에 아무도 못 읽는다.

1. `ledger.md` 헤더 — 판정 · open BLOCKER 수
2. `ledger.md` 에서 **`open`·`fixing` 행만** — 이게 할 일이다
3. 해당 축 파일의 그 ID 절만
4. 마지막 `fixes-roundN.md` 의 「드러난 다음 결함」

그리고 **새 라운드 파일을 만들어** 작업한다. 기존 라운드 파일을 고치지 마라 — 이력이 사라진다.

### 재진입 시 반드시 의심할 것
- **대장의 `verified` 도 낡는다.** 그 뒤 코드가 바뀌었으면 다시 재야 한다. 「언제 잰 값인가」를 항상 확인하라.
- **감사 보고서 자체가 틀렸을 수 있다.** 이미 고쳐진 것을 결함으로 올린 사례가 실제로 있었다(stale). 착수 전에 **현재 코드로 재확인**하라.
- **`rejected` 를 다시 열지 마라** — 반박 근거를 먼저 읽고, 그 근거가 틀렸을 때만 새 ID 로 다시 올린다.

## 최종 통합 검증 (`99-final-verification.md`)

- **전 게이트를 경합 없는 창에서 한 번에** 재실측(측정 위생은 `measurement-hygiene.md`)
- **이음매 점검** — 여러 라운드가 서로 어긋났는지. 실측 사례: 같은 카드 안 두 숫자가 갈림 · 알림 링크 문법과 프런트 딥링크 불일치 · 표시 값과 강제 값이 다름
- **방치 항목 점검** — 「판단 필요」·「겹침 회피」로 아무도 안 가져간 항목이 남았는지. **이게 가장 조용히 새는 자리다**
- **라이브로 보지 못한 것을 명시** — 무엇을 확인하지 못했는지 적어야 다음 사람이 그걸 확인한다
